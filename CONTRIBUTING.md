# Contributing

This repo is the documentation site at
[docs.openpreflight.xyz](https://docs.openpreflight.xyz), built on Astro and
Starlight. It is the source of truth for the docs. The tool it documents lives in
[openpreflight/openpreflight](https://github.com/openpreflight/openpreflight);
for the Go build and test loop, see
[Development](https://docs.openpreflight.xyz/contributing/development/).

## Dev loop

```bash
npm ci
npm run dev             # local preview
npm run build           # static output in dist/
npm run check-links     # required paths, internal hrefs, unique descriptions
npm run check-style     # the writing rules below
```

`check-links` runs against `dist/`, so build first. It fails on a missing
required path, a broken internal link, or a page that uses the site-wide
description. If you move a page, add a redirect in `astro.config.mjs` and keep
the old path in the `required` list.

## Writing docs

The pages use [ASD-STE100](https://www.asd-ste100.org/) Simplified Technical
English (Issue 9, January 2025). These are the rules:

1. Each page is a procedure or a description. A procedure gives numbered steps.
   A description gives tables and short paragraphs.
2. Max 20 words in a sentence in a procedure step. Max 25 words in a sentence in
   a description.
3. Max 6 sentences in a paragraph, with one topic in each paragraph.
4. Give one instruction in each step. Use the imperative: "Set `CI_SECRET_KEY`."
5. Put the condition first: "If the socket is not readable, set `DOCKER_GID`."
6. Use the active voice where possible. Use the simple present, simple past and
   simple future tenses. Do not use `-ing` verb forms, except in technical names.
7. Do not use contractions or phrasal verbs. Keep the articles ("the", "a").
8. Max 3 words in a noun cluster. Use a preposition to break a longer cluster.
9. Give a warning as a `:::caution` block. Start it with a command, then give
   the reason.
10. Use the terms in the [glossary](https://docs.openpreflight.xyz/reference/glossary/)
    only. You can also use technical names (Check Run, SHA, webhook, env var names).
11. Do not change code blocks, CLI output, JSON, log lines or UI labels.
12. Write each fact on one page only. Other pages give one sentence and a link.

`check-style` fails on an em dash, `OpenPreflight`, a contraction, a sentence
that is too long, or a word from the house list in `scripts/check-style.mjs`.
It does not check all of the STE dictionary. The house list gives the approved
word for each word that it refuses.

Page template for a procedure:

```md
One sentence: what this procedure does.

## Before you start
- prerequisite

## Procedure
1. Command.
2. Command.

## Result
What you see when the procedure is complete.

## Related
- link
```

Page template for a description:

```md
One sentence: what this page describes.

## Topic
A table, or up to 6 short sentences.
```

Other rules for the site:

- Pages are in `src/content/docs/`, with one directory for each sidebar group.
  Groups are autogenerated, except Reference. To add a page to a group, put the
  file in the directory and set `sidebar.order` in its frontmatter. A new
  Reference page or a new group must also go in `astro.config.mjs`.
- Write what the code does today, not what is planned. If a change here
  documents new behaviour, merge the pull request in
  [openpreflight/openpreflight](https://github.com/openpreflight/openpreflight)
  first or at the same time.
- Write an architecture decision in `src/content/docs/reference/decisions/` as a
  new numbered record. Do not edit an old record to change its decision.
- `design.md` is the brand spec, which the marketing site also uses. It is not
  served. Do not move it into `public/`.

## Pull requests

- One concern for each PR.
- `npm run build && npm run check-links && npm run check-style` clean before you
  open it.
- Security-sensitive reports go through
  [openpreflight/openpreflight SECURITY.md](https://github.com/openpreflight/openpreflight/blob/main/SECURITY.md),
  not a public issue.
